# SysAdmin API v1 on `intersystemsdc/iris-community:latest` (IRIS 2026.1), 2026-09-17

Investigation only. Nothing in the spec, plan or tasks changed. Machine-readable data:
- `v1-api-2026.1.json`: routes, per-operation coverage, response-shape probe, privileges per endpoint.
- `v1-api-2026.1-instance-spec.json`: the specification the instance itself serves.

Target: `iris --version` 2026.1.0.234.1, `IRIS for UNIX … 2026.1 (Build 234U)`, product `iris`. The
container was started with the entrypoint override (research R2) and default passwords unexpired
(R3), then removed.

## 1. Base, routes, specification

| Question | Finding |
|---|---|
| Base | `/api/admin/info` (`apiVersion: 1`) plus `/api/admin/v1/<route>`. Dispatcher `Api.Admin` (not `%Api.Admin`) forwards `/v1` to `Api.Admin.v1.Dispatch`. `/api/admin/v1/` alone is 404, and every `/api/admin/v2/*` is 404 |
| Routes | **197** in the `/v1` UrlMap, plus `/info`. Lists use a singular path with a trailing slash (`GET /v1/task/`); details drop it (`GET /v1/task`) |
| Actions | Several are `PATCH` on the resource (`/v1/task`, `/v1/task/manager`, `/v1/process`, `/v1/els`, `/v1/async-result`). SQL privilege grant/revoke is `PUT`/`DELETE`; the wallet collection lives at `/v1/wallet` |
| JWT | `POST /api/admin/login` → 404. Only Basic or session authentication |
| Published specification | **None from InterSystems.** The instance serves one at `/api/mgmnt/v1/%SYS/spec/api/admin`, but it is Swagger 2.0 **generated from the UrlMap**: 195 operations, empty `info`, **no parameters, no request or response schemas, no privilege declarations** (no `%Admin_` anywhere) |
| Privileges | Not published. They exist only inside compiled endpoint classes: `Api.Admin.v1.Endpoints.*:ResourcesOR()` returns an OR list per class and request type (47 classes; LDAP and Task.CRUD vary by type). Sampled values match the v2 declarations (Role → Secure; Task list/get/put/delete → Task or Operate, Task patch/actions → Task; LDAP read → Secure or Operate, LDAP write → Secure). **The binding from route to endpoint class and type is not published**, and the dispatch methods ship without source |
| In-process auth path | `confirmed_present`. The FDVerify.InProcess probe, pointed at `Api.Admin`, reached `/info`, `/v1/security/role/`, `/v1/process/` and `/v1/task/` with the IRIS session cookie only |

## 2. Coverage against the six axes and `docs/api-coverage.md`

Each of the 273 v2 operations was classified:
- **same shape**: same method and path under `/v1`;
- **different shape**: served by a v1 route with another method or path, whose request body the v1
  specification does not document;
- **absent**.

| Domain (api-coverage §) | v2 operations | Same shape | Different shape | Absent | Missing families |
|---|---|---|---|---|---|
| 0 Session | 5 | 0 | 1 (`/info`) | 4 | `/login`, `/logout`, `/refresh`, `/revoke` |
| 1 Web apps and APIs | 8 | 8 | 0 | 0 | none |
| 2 Permissions | 31 | 23 | 8 | 0 | none (SQL grant/revoke via PUT/DELETE) |
| 3 Security and secrets | 89 | 83 | 6 | 0 | none |
| 4 Tasks | 24 | 16 | 8 | 0 | none (run/suspend/resume via PATCH) |
| 5 Operating system | 102 | 38 | 5 | **59** | `namespace` (18), `database-dir` (15), `ecp` (13), `fs-access-purpose` (7), `database` (4), `lock` (2) |
| 6 Logs | 14 | 5 | 0 | **9** | `journal` (all 9) |
| **Total** | **273** | **173** | **28** | **72** | |

The v1 also has 4 routes with no v2 equivalent: `HEAD` on the three SQL privilege routes and
`POST /v1/security/ssl-configuration/private-key-password`.

By contest axis:
- **Web apps, Permissions, Security, Tasks**: every operation has a v1 route, 28 of them with a
  different method, path or body.
- **Operating system** keeps processes, monitor dashboards, devices, license, DocDB, external
  language servers and web sessions. It **loses disks/databases**, namespaces, ECP and locks.
  "disks" is named in the contest statement, and RN-FD-19 requires disk per database: there is no
  `database-dir/info` and no asynchronous database metrics, so the Disk vital cannot be computed.
- **Logs** keeps the audit configuration and records. It **loses the journal**. The native
  providers (`messages.log`, alerts, interoperability) do not depend on the API.

**Response shapes.**
- 43 parameterless GET operations were called live.
- 31 of the 33 that returned data have exactly the v2 schema field set.
- The 2 differences:
  - `processes`: `EXEname`/`EXEName`, the same casing issue on 2026.2, so a v2 spec issue;
  - `services`: `EnabledBoolean` absent.
- 10 lists were empty on a fresh instance.
- `oauth2/server` returned 404 (not configured).
- `/info` has the same keys as v2, except the `FileSystemAccess` privilege, whose resource does not
  exist in 2026.1.

## 3. Answer: useful partial degradation, or refusal?

**Technically, a useful partial mode exists; under the current constitution and PRD, the FR-012a
refusal is the only honest outcome.**

What makes partial mode useful:
- 201 of 273 operations have a v1 route;
- four of the six axes are fully reachable;
- response shapes match v2;
- the in-process sign-in path works as designed.

What prevents doing it honestly today:

1. **Constitution III cannot be satisfied as written.** The capability map must be "derived from
   the privilege each API operation declares". The v1 declares none in any published form. The
   only sources are:
   - the v2 spec, which describes a different API version, for the 201 mapped operations;
   - the implementation's `ResourcesOR()` in internal classes, whose route binding is unpublished.

   Either choice is a reinterpretation of the principle, and the constitution routes that through
   an explicit amendment.
2. **Constitution I names `/api/admin/v2` and `docs/sysadmin-api-v2.json` as the source.** 28
   operations would need translation to v1 methods, paths and bodies that the v1 specification
   does not document (no request schemas), meaning bodies inferred from undocumented behavior.
3. **A product requirement cannot be met, not merely degraded.** RN-FD-19 makes disk per database
   a minimum instrument ("absence of any one is a requirement failure"). Namespaces, databases,
   ECP and the journal log source have no v1 route. Degradation with a reason (Principle VIII)
   covers features missing on an edition or version; here the System and Logs axes would lose
   parts the contest names explicitly.

What a partial mode would need, if wanted:
- a constitution amendment covering v1 as a secondary source and how its privileges are derived;
- a v1 adapter: path, method and list-suffix translation plus the 28 translated operations;
- a per-operation availability map, generated from this report;
- System and Logs screens designed to show the absent families disabled, with the reason.

Nothing in feature 001 blocks adding this later: the capability map, `Admin.Client` and the
domain model are where the adapter would plug in.

**Context for the decision.** The observed tags show `latest` = `latest-em` = 2026.1 and
`latest-cd` = 2026.2. `latest` follows the extended-maintenance line, and the install already pins
the 2026.2 images, which satisfies the contest's "IRIS Community Edition or IRIS for Health
Community Edition" requirement. Refusal only affects someone who points FlightDeck at a 2026.1
instance on purpose.
